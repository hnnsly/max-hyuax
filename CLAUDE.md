> **Проект:** «Адресная табличка» — сервис коллективных заявок о неисправностях общего имущества МКД  
> **Контекст:** Трек «Умный город» (кейс «Умный дом»), Хакатон платформы MAX  
> **База знаний и требования:** [`hack-docs/INDEX.md`](hack-docs/INDEX.md) (точка входа для архитектуры, SRS, UX и ADR)

## 1. Главные правила и ограничения хакатона

1. **Разделение двух миров (ADR-001):**
   - `hack-docs/` — внутренняя база знаний (исследования, интервью, SRS, ADR, риски). **В финальную сдачу не входит.**
   - `docs/` и `README.md` в корне — документация продукта для жюри и пользователей. Пишется чисто, строго для людей, без frontmatter и без упоминания ИИ.
2. **Правило «Без ИИ-меток» (п. 9.5 правил, ADR-001, ADR-007):**
   - Никаких служебных комментариев вида `Generated by Claude`, `AI assistant`, ИИ-трейлеров в коммитах или артефактах сдачи.
   - Любой код, предложенный агентами, проходит ревью человеком из команды.
3. **Конфиденциальность кейса (п. 11.3 правил):**
   - Исходный рабочий репозиторий является приватным. Сдача осуществляется из отдельного чистого репозитория без служебных файлов (`hack-docs/`, `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.obsidian/`).
4. **Собственное API (ADR-006):**
   - Бэкенд объявляется собственным API. Обязательны: HTTPS-адрес, `api/openapi.yaml` (3.1), `DATA-API.yaml` с обязательными проверками, сидированные тестовые учетные записи (`/auth/demo`).
5. **Воспроизводимость Docker (DEP-01, DEP-02):**
   - Сборка `docker compose up --build` должна занимать **≤ 5 минут** на чистой машине.
   - Никаких рабочих секретов и токенов в репозитории — только `.env.example`.

## 2. Архитектура и стек технологий

- **Основной язык бэкенда:** Go (Go 1.22+)
  - **HTTP-фреймворк:** Fiber v3 (и для REST API `/api/v1`, и для вебхука бота `/webhook/max`).
  - **База данных:** PostgreSQL 16 + драйвер `pgx/v5`.
  - **Генерация запросов:** `sqlc` (типобезопасный SQL без ORM).
  - **Миграции:** `goose` (чистые `.sql` миграции в `backend/db/migrations`).
  - **Хранилище файлов:** MinIO (S3 API) для фотографий дефектов и сгенерированных PDF.
  - **Bot API клиент:** `github.com/max-messenger/max-bot-api-client-go` за интерфейсом порта `MaxBotGateway`.
  - **LLM:** Self-hosted Ollama (модель класса Qwen 2.5 3B/7B Instruct) за интерфейсом `LLMAssistant` с обязательным автоматическим откатом на правила при таймауте (>5-8с) или сбое.
- **Фронтенд мини-приложения:**
  - **Стек:** Vite + React (JavaScript per ADR-003/006) + библиотека компонентов MAX UI.
  - **Интеграция с платформой:** MAX Bridge (`window.WebApp`).
  - **Дизайн-система:** «Адресная табличка» (`hack-docs/design/tokens.css` и `hack-docs/design/DESIGN-SYSTEM.md`).
- **Инфраструктура и прокси:**
  - **Caddy:** автоматический TLS, маршрутизация запросов.
  - **Корневой сертификат Минцифры:** обязателен внутри Docker-образов для исходящих вызовов к `platform-api2.max.ru`.

## 3. Архитектурные паттерны и организация кода

### 3.1 Структура бэкенда (Порты и Адаптеры)
```
backend/
├── cmd/
│   └── server/          # Точка входа: инициализация HTTP-сервера, адаптеров и воркеров
├── internal/
│   ├── domain/          # Чистые сущности и бизнес-правила (Issue, House, DeadlineRule)
│   ├── app/             # Сервисы сценариев (CreateIssue, JoinIssue, ChangeStatus)
│   ├── ports/           # Интерфейсы репозиториев, бота, хранилища, LLM
│   ├── adapters/
│   │   ├── http/        # Роуты Fiber v3, валидация OpenAPI, auth middleware
│   │   ├── maxbot/      # Обработка вебхука, отправка и редактирование сообщений
│   │   ├── postgres/    # Реализация портов на sqlc
│   │   ├── minio/       # Реализация хранилища файлов S3
│   │   └── llm/         # Клиент Ollama + fallback на правила
│   └── worker/          # Outbox-воркер отправки сообщений, таймер SLA
├── db/
│   ├── migrations/      # SQL-миграции goose
│   └── queries/         # SQL-запросы для генерации sqlc
└── go.mod
```

### 3.2 Ключевые механизмы
1. **Contract-First:** Изменения в API вносятся сначала в `api/openapi.yaml` и согласуются обеими парами.
2. **Вебхук и лимиты:**
   - Вебхук проверяет `X-Max-Bot-Api-Secret`, дедуплицирует событие по `update_id` через БД и отвечает `200 OK` немедленно (<100 мс).
   - Любая отправка в MAX идет через таблицу `outbox_messages` и фоновый воркер с соблюдением лимитов: не более **2 rps на чат** и **30 rps глобально**.
3. **Живая карточка (Live Card):**
   - У каждого участника сохраняется `message_id` карточки в чате с ботом (`bot_message_refs`).
   - При смене статуса заявки УК в outbox ставятся задачи `PUT /messages` для обновления карточки у всех участников без отправки спама новыми сообщениями.
4. **Безопасность и ПДн (152-ФЗ):**
   - Соседи в интерфейсе видят **только счетчик** участников («сообщили 12 соседей»), но не имена и квартиры.
   - Телефон запрашивается только через `requestContact` с проверкой HMAC-хэша и виден только УК.
   - При загрузке фото обязательно удаляются метаданные EXIF (геотеги, модель камеры).
5. **Автокомплит адресов и геопоиск (OpenStreetMap + Photon):**
   - Интеграция открытого геокодера OpenStreetMap (Photon API `https://photon.komoot.io`) через Go-прокси с in-memory LRU-кэшированием и ограничением bbox по Москве (`37.3,55.5,37.9,56.0`).
   - Эндпоинты `GET /api/v1/geo/suggest?q=...` (автокомплит для `SearchInput` мини-приложения) и `GET /api/v1/geo/reverse?lat=...&lon=...` (обратное геокодирование координат GPS из бота).
   - Привязка выбранного адреса OSM к управляющей компании из локального реестра `houses` в PostgreSQL; локальный fallback при отсутствии внешней сети.
   - Отображение мини-карты OpenStreetMap (Leaflet + OSM tiles) в мини-приложении.

## 4. Распределение задач по командам

- **Пара A («Прием и UX»):**
  - Бот: диалоговый сбор проблемы, команды `/start`, `/help`, обработка геолокации.
  - Аутентификация: валидация `initData` по HMAC-SHA256, модалка согласия с ПДн.
  - Мини-приложение: форма подачи заявки, выбор подъезда/объекта, привязка к дому.
  - Интеграция Ollama: подсказка категории со строгим таймаутом и откатом на селект.
  - Шеринг: карточка для пересылки в домовой чат (`shareMaxContent`).
- **Пара B («Жизненный цикл и УК»):**
  - Домен Issue: логика создания, дедупликация (поиск открытых дефектов по объекту), функция «Это и у меня» (409 при повторе).
  - Уведомления: таблица outbox, воркер отправки, редактирование сообщений бота.
  - Кабинет УК: список заявок, фильтрация, смена статуса с комментарием.
  - Сроки и SLA: справочник норм (ПП 416), производственный календарь, фиксация просрочки.
  - Эскалация: генерация PDF-обращения в Мосжилинспекцию.
  - Дашборд: расчет метрик (время реакции, отсеянные дубли, процент просрочки).

## 5. Конвенции разработки и Git

1. **Коммиты:** Conventional Commits на английском языке:
   - `feat: add initData HMAC validator with unit tests`
   - `fix(worker): handle rate limit 429 in outbox sender`
   - `docs: update API contract for issue joining`
2. **Ветки:** Короткоживущие фиче-ветки от `master`/`main`:
   - `feat/pair-a-auth-validator`
   - `feat/pair-b-issue-domain`
3. **Код:**
   - Go: следовать `modern-go-guidelines`, проверка через `go vet ./...` и `golangci-lint`.
   - React: функциональные компоненты, хуки, JSDoc для объектов API, ESLint.
   - Схемы в документации: строго в формате **ASCII art**.

## 6. Чек-лист проверки готовности задачи (Definition of Done)

Перед тем как фича считается принятой:
- [ ] Написаны и проходят юнит-тесты на Go (`go test ./...`).
- [ ] Эндпоинты строго соответствуют контракту `api/openapi.yaml`.
- [ ] В UI мини-приложения реализованы все 4 состояния: загрузка (Spinner), успех, ошибка (Toast/Banner), пустой список (EmptyState).
- [ ] Сценарий проверен на мобильном клиенте и в десктопном браузере (Desktop Web).
- [ ] Отсутствуют хардкод токенов, ключей и персональных данных.
- [ ] Изменения отражены в соответствующем файле документации `docs/`.
