# Данные

## Что хранится

| Таблица | Содержимое |
|---|---|
| `organizations` | управляющие организации: название, телефоны, график |
| `houses` | дома: адрес, район, год постройки, этажность, подъезды, УК |
| `entrances` | подъезды |
| `asset_objects` | объекты общего имущества с QR-кодами: лифты, освещение, кровля, мусоропровод |
| `users` | пользователи: имя из MAX, роль, дом, согласие, отметка об удалении |
| `issues` | заявки: категория, статус, ответственный, срок, последний комментарий УК |
| `issue_participants` | кто присоединился к заявке |
| `issue_events` | журнал событий заявки |
| `processed_updates` | ключи обработанных событий бота (защита от повторной доставки) |
| `outbox` | очередь исходящих сообщений бота: адресат, вид, попытки, время следующей попытки |
| `bot_cards` | какое сообщение в чате с ботом — живая карточка заявки у участника |

Схема создаётся миграциями из `backend/internal/storage/postgres/migrations` при старте сервиса.

## Модельные и синтетические данные

Для демонстрации миграции `00002_demo_seed.sql` и `00003_demo_seed_history.sql` создают:

- **УК «Ореховый квартал»:** организация модельная, название и телефоны условные.
- **Шесть домов на Ореховом бульваре (район Зябликово, Москва):** улица реальная, а годы постройки, этажность, число подъездов и координаты условные.
- **Объекты с QR-кодами:** лифт и освещение в каждом подъезде, кровля и мусоропровод каждого дома.
- **Три демо-пользователя:** два жителя и сотрудник УК.
- **Три синтетические заявки** в статусах «в работе», «отправлена» и «выполнена».

Модельные записи домов и организаций помечены полем `source = 'model'`, API отдаёт это поле, чтобы интерфейс показывал пометку.

Миграция `00006_sample_metrics.sql` добавляет пример данных для метрик УК:

- **12 синтетических жителей** без имён, телефонов и аккаунтов MAX. Они нужны только для счётчиков участников.
- **22 синтетические заявки** по шести домам за последние 16 дней. У них есть история статусов, присоединения соседей, закрытия в срок и с опозданием, две открытые просроченные заявки.
- **Пометка.** Синтетические заявки, включая три демо-заявки, помечены полем `issues.sample = true`. Экран метрик в таком случае подписан «Пример данных».
- **Свежесть дат.** При включённом демо-входе (`DEMO_AUTH_ENABLED=true`) сервис раз в 10 минут сдвигает даты синтетических заявок вперёд на целое число дней. Благодаря этому пример не устаревает, а порядок событий и интервалы между ними сохраняются. Заявки настоящих пользователей не затрагиваются.

## Сроки ответа

Сроки заданы в справочнике категорий (`backend/internal/domain/rules`) в рабочих днях. Это модельные значения для демонстрации. Перед реальным пилотом их нужно сверить с регламентом управляющей компании и нормативами. Праздничные дни пока не учитываются.

## Персональные данные

- Имя пользователя приходит из MAX при входе.
- Телефон сейчас не собирается. Поле в таблице `users` зарезервировано: номер будет запрашиваться только с согласия жителя и будет виден только УК.
- Соседи видят только число участников заявки.
- При удалении аккаунта имя, телефон и согласие стираются, заявки остаются без данных автора.
  - Удалить аккаунт можно на экране «Мой дом»: пункт «Удалить аккаунт», затем подтверждение в нижнем листе. В API это `DELETE /me`.
  - Если житель снова откроет приложение в MAX, аккаунт начнётся с чистого листа, и согласие нужно будет дать заново.
  - Демо-пользователь после удаления восстанавливается при следующем демо-входе, тоже без согласия. Так проверка удаления не ломает демо для других проверяющих.
- Логи не содержат персональных данных и текстов обращений.
