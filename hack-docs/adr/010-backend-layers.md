# ADR-010: Бэкенд — три слоя (транспорт, приложение, хранилище) и DDD-lite

## Контекст
- Команда хочет трёхслойную архитектуру с DDD-lite и чётким разделением ответственности, но без накладных расходов там, где они не окупаются (YAGNI).
- До сдачи 7 дней. Код пишет тот, кто взялся, и оставляет заметку передачи ([HANDOFF](../HANDOFF.md)).
- Уточняет структуру из [ADR-003](003-backend-architecture.md), не отменяя стек: Go 1.27.1, Fiber v3, pgx + sqlc, PostgreSQL, goose.

## Решение

```
backend/
  cmd/api/                точка сборки: конфиг, зависимости, запуск HTTP, бота и фоновых задач
  internal/
    domain/               ядро, без зависимостей от Fiber, SQL и MAX
      issue/              агрегат Issue: статусы и переходы, участники, срок и просрочка, доменные события
      house/              House, Entrance, AssetObject, Organization (модели чтения)
      user/               User, Role, согласие на обработку ПДн
      rules/              справочник категорий: ответственный, основание, срок (данные)
    app/                  сценарии и порты (интерфейсы)
    transport/            входящие: http (Fiber), bot (обновления MAX), jobs (таймеры)
    storage/              исходящие: postgres (репозитории, миграции), maxapi (клиент Bot API)
```

**Зависимости:**
- `domain` не зависит ни от чего;
- `app` зависит только от `domain`;
- `transport` и `storage` зависят от `app` и `domain` (HTTP — пакет `transport/httpapi`);
- единственное исключение: `transport/bot` импортирует типы протокола и клиент из `storage/maxapi`. Входящие события и ответы бота — один и тот же протокол MAX, дублировать его типы в двух пакетах незачем. Уведомления из сценариев (живая карточка) идут через порт `app`, а не напрямую;
- собирает всё вместе только `cmd/api`.

**DDD-lite:**
- Агрегат — `Issue`; инварианты (переходы статусов, повторное присоединение, срок) проверяются внутри него.
- Методы агрегата возвращают доменные события. Сценарий записывает их в outbox в той же транзакции, что и изменение агрегата.
- Value objects: `Status`, `Category`, `Deadline`, идентификаторы.

**YAGNI — сознательно не делаем:**
| Не делаем | Почему |
|---|---|
| CQRS, шину событий | одного outbox достаточно |
| DTO на каждый сценарий | входы сценариев — простые структуры, JSON-маппинг только в транспорте |
| универсальные репозитории, генераторы маппинга | sqlc-модели переводятся в доменные внутри репозитория |
| LLM-классификатор с первого дня | сначала правила по ключевым словам за портом `Classifier`; Ollama — Should |
| порт `FileStore` заранее | появится вместе с фото (Should) |
| генерацию кода по OpenAPI | `api/openapi.yaml` и хендлеры пишутся руками |
| SDK MAX, если он отстаёт от `platform-api2` | свой тонкий клиент на ~6 методов |

## Рассмотренные альтернативы
| Вариант | Почему не выбран |
|---|---|
| Классическая гексагональная структура с `ports/` и `adapters/` | та же идея, но команда просила три слоя с понятными названиями |
| Полный DDD (bounded contexts, репозиторий на агрегат, шина событий) | избыточно для MVP за 7 дней |
| Плоский сервис без слоёв | сложнее поддерживать и объяснять жюри |

## Последствия
- **Плюсы:** понятные границы для любого, кто подхватывает работу; домен тестируется без базы; замена хранилища и шлюзов не трогает сценарии.
- **Минусы:** немного больше файлов, чем в плоском сервисе.
- **Задачи:** держать дерево и правила слоёв в `CLAUDE.md` и `docs/architecture.md` актуальными.
