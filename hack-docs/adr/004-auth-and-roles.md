# ADR-004: Аутентификация по initData и модель ролей

## Контекст
- Мини-приложение получает `initData` с HMAC-подписью; `initDataUnsafe` доверять нельзя. Рекомендуемая свежесть `auth_date` — 1 час ([webapps/validation.md](../dev-max/docs/webapps/validation.md)).
- Мини-приложение может быть открыто дольше часа → нужен обмен initData на собственную сессию.
- Собственное API объявляется для проверки ([ADR-006](006-api-contract.md)) → проверяющим нужны тестовые учётные записи ролей без клиента MAX.
- Роль «УК» в демо выполняет тестовая учётка ([ADR-002](002-product-scope.md)).

## Решение

### Вход
1. `POST /auth/max` принимает сырую строку `initData`.
2. Сервер проверяет HMAC (`secret = HMAC_SHA256("WebAppData", BOT_TOKEN)`), уникальность ключей и свежесть `auth_date` (≤ 1 ч).
3. Сервер находит или создаёт `User` по `user.id` MAX и выдаёт сессионный токен (подписанный, срок 12 ч, в заголовке `Authorization: Bearer`).
4. Телефон — только через `requestContact` с проверкой hash (`HMAC_SHA256(authDate+phone+userId, botToken)` по документации Bridge).
5. Бот идентифицирует пользователя по `user_id` из событий; связь бот ↔ мини-приложение — через этот же `user_id`.

### Роли
| Роль | Назначение | Как выдаётся |
|---|---|---|
| `resident` | по умолчанию после входа | автоматически |
| `uk_operator` | сотрудник УК: проблемы своих домов, смена статуса, дашборд | seed / админ |
| `chairman` | председатель совета (Could) | seed / админ |
| `contractor` | подрядчик (Could) | seed / админ |
| `admin` | справочники и роли | seed |

Проверка прав — только на сервере (RBAC-middleware + проверка принадлежности дома).

### Демо-режим для проверяющих
- `POST /auth/demo {"role": "resident" | "uk_operator" | ...}` возвращает сессию тестового пользователя роли.
- **Работает только при `DEMO_AUTH_ENABLED=true`**; на демо-стенде включён, в `.env.example` по умолчанию `false`.
- Тестовые пользователи и их дома создаются детерминированным seed ([data-model](../requirements/data-model.md)).
- Учётные данные демо-ролей указываются на первом слайде и в `DATA-API.yaml`.

## Рассмотренные альтернативы
| Вариант | Почему не выбран |
|---|---|
| initData в каждом запросе | ломается через час открытого приложения |
| Логин и пароль | лишний шаг, против UX MAX |
| Статичные API-ключи ролей всегда включены | риск утечки на проде |

## Последствия
- **Плюсы:** безопасный вход без паролей; проверяемость API; ролевая модель готова к реальным УК.
- **Минусы:** демо-режим нужно явно отключать вне демо-стенда; ключ подписи сессий — ещё один секрет.
- **Задачи:** валидатор initData с юнит-тестами (Спайк 0, без токена — на своих подписях); middleware ролей; seed демо-ролей.
