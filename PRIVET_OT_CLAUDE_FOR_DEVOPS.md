## Почему срочно

- Мини-приложение в MAX открывается по URL, который прописывается в настройках бота.
- **Любая правка настроек бота (включая этот URL) модерируется до 48 рабочих часов.** 48 рабочих часов — это до шести рабочих дней, а сдача 30.09, заморозка кода 29.09 днём.
- Мы про это вспомнили поздно. Если URL не отправить на модерацию сегодня-завтра, жюри может увидеть бота без мини-приложения.
- Хорошая новость: за URL может пока стоять что угодно. Модерируется **адрес**, а код за ним мы потом меняем сколько угодно без повторной модерации. Поэтому URL должен быть **постоянным**: тот же домен и путь `/` до конца хакатона.

## Что сделать (порядок важен)

### 1. Сегодня: мини-приложение по HTTPS и URL на модерацию (этап А)

Обновление от 25.09: заглушки больше нет, `web` сразу собирает настоящее мини-приложение (`docker compose up -d --build web`). Бэкенд тоже готов, можно сразу делать и этап Б из `hack-docs/DEVOPS.md`.

1. VPS в РФ, Docker + compose plugin, открыты порты 80 и 443.
2. A-запись домена указывает на VPS.
3. На сервере:
   ```bash
   git clone https://github.com/hnnsly/max-hyuax.git /opt/dom-max
   cd /opt/dom-max/deploy
   cp .env.example .env        # вписать DOMAIN=ваш.домен
   docker compose up -d --build web
   ```
4. Открыть `https://<домен>/`: должно открыться мини-приложение с валидным сертификатом (замок в браузере). Без валидного HTTPS модерацию не пройти.
5. **Сразу** прописать URL: https://business.max.ru/self → «Чат-боты» → `t105_hakaton_max_bot` → «⋮» → «Настройки» → адрес мини-приложения `https://<домен>/` → сохранить.
6. Написать домен в чат команды и в `hack-docs/HANDOFF.md` (раздел «Открытые вопросы»).

Если репозиторий приватный, для `git clone` на сервере нужен deploy key (GitHub → Settings → Deploy keys, только чтение).

### 2. Затем: включить автодеплой

Пайплайн `.github/workflows/ci.yml` уже в репозитории, комментарии внутри. Нужно только завести секреты (GitHub → Settings → Secrets and variables → Actions):

| Секрет | Значение |
|---|---|
| `VPS_HOST` | IP или домен сервера |
| `VPS_USER` | пользователь SSH, состоит в группе `docker` |
| `VPS_SSH_KEY` | приватный ключ целиком; публичный — в `~/.ssh/authorized_keys` на VPS |
| `DEPLOY_PATH` | `/opt/dom-max` (где лежит клон) |

Пока секретов нет, job `deploy` пропускается с пометкой, проверки работают. После настройки каждый push в `master` обновляет код на сервере и делает `docker compose up -d --build`.

Осторожно с `deploy/.env`: деплой делает `git reset --hard`. Если `deploy/.env` закоммичен в репозиторий, серверная версия будет перезаписана версией из git. Либо держите на сервере правильный `DOMAIN` и в закоммиченном файле, либо не коммитьте `deploy/.env`.

### 3. Если есть силы: капелька бэкенда в деплой

Бэкенд (`backend/`, Go 1.27.1) уже умеет: бот в режиме long polling отвечает на `/start`. Webhook и HTTP API появятся 24.09. Чтобы бот жил на сервере, а не на ноутбуке:

1. `backend/Dockerfile`, многоэтапный:
   - сборка: образ `golang:1.27`, `go build -o /api ./cmd/api` (с `CGO_ENABLED=0`);
   - запуск: `alpine` или `distroless`, **с корневым сертификатом Минцифры** (Russian Trusted Root CA, PEM) в системном хранилище. Иначе запросы к `platform-api2.max.ru` падают на TLS. Альтернатива: положить PEM в образ и задать `MAX_API_CA_FILE=/путь/к/ca.pem`.
2. Сервис `api` в `deploy/compose.yaml`: `build: ../backend`, переменные `MAX_BOT_TOKEN` (токен в `CLAUDE.md`), `BOT_MODE=polling`, `restart: unless-stopped`. Порт наружу не нужен: Caddy сам ходит на `api:8080`, а HTTP-сервер появится позже.
3. **Никогда не запускать `MAX_API_INSECURE_TLS=true` на сервере**: это флаг только для ноутбука разработчика.
4. Одновременно работать может только один экземпляр бота в режиме polling (иначе они делят события). Когда бот поднят на сервере, локально его не запускаем.

Проверка: в логах `docker compose logs api` есть строка `bot authorized`, а бот https://max.ru/t105_hakaton_max_bot отвечает на `/start` приветствием с двумя кнопками.

Команды для локальной проверки бэкенда — в `CLAUDE.md`, раздел «Команды».
